# drive-spec

`/drive-spec <spec-issue> [--base <branch>] [--sequential] [--dry-run]`

Drive a spec issue from its tracer-bullet issues to one draft PR `spec branch → base`. Each slice is built in its own worktree and merged into the spec branch, which lives in a worktree of its own. The checkout you are standing in is never touched, so several sessions can drive several specs in one repo at once.

The tickets are a task graph. Slices whose blockers have all closed form the **frontier**. State lives only in the tracker and the branches, so any session can resume any spec, and the same slice never builds twice.

`drive-spec`, the script beside this file, runs every deterministic part of a step; `drive-spec --help` lists its commands. Its refusals (exit 2) name the broken rule: fix that, never route around it. A change never edits what judges it: `verify` stops a worktree after `maxReds` reds in a row, `integrate` refuses a deleted test or changed gate file its deviations leave out, and the reviewer reads the rules from base. A red verdict stands for its head: `verify` never reruns it, and only a new commit gets a new verdict. A red a subagent reports, a suspected flake included, goes back to a fixer with the failing test named, or to the operator through `drive-spec ask` when no one can trace its cause; the dispatcher runs `verify` only on a head no gate has judged.

Reference, read when a step points at it:

- [`TRACKER.md`](TRACKER.md) — discovery, blockers, labels, the progress and status comments, integration and landing, PRs, halting.
- [`WORKTREES.md`](WORKTREES.md) — root, naming, notes directory, create, bootstrap, resume rules, cleanup.
- [`EXPLORER.md`](EXPLORER.md), [`REVIEWER.md`](REVIEWER.md), [`REVIEW-FIXER.md`](REVIEW-FIXER.md) — the subagent briefs: the script fills each into a file and prints `Read <file> and follow it.`, the subagent's whole prompt.
- [`IMPLEMENTER.md`](IMPLEMENTER.md), [`MERGER.md`](MERGER.md) — the briefs of the agents `drive-spec build` launches in step 6, prompted the same way.
- [`STATUS.md`](STATUS.md) — the status file, its states, how to ask the operator a question, and the inbox.

Every step ends in a `drive-spec` command that marks the next step begun in the status file per STATUS.md; the step names it. Its exit code is the verdict, so run each command bare, with nothing piped after it. `drive-spec next <spec>` prints the command that carries a run on, from its status file: run it first when resuming. `build`, `verify`, `open` and `start` can run for an hour: run each through the Bash tool's `run_in_background`, with no `--wait-minutes` and no `timeout` (a background command's `timeout` kills it), then end the turn; the harness wakes you with its exit code when it ends, and its output file holds what it printed. That notification is the only wake-up: a command detached any other way (`&`, `nohup`) ends the turn with nothing set to resume it. Where background tasks are unavailable, run them in the foreground with `--wait-minutes 9` and a 10-minute Bash timeout: exit 6 means a gate, an agent or a bootstrap is still running, and the same command again picks up where it stopped. Commands that read the dispatcher's inbox (STATUS.md, Inbox) exit 5 while notes wait: act on them, then run the command again. A decision only the operator can make goes through `drive-spec ask` and `drive-spec answered` (STATUS.md, Questions).

Communicate with subagents through context pointers: issue numbers, worktree paths, research notes, the `drive-spec verify` command. Everything else they read themselves.

An interim notification from a background subagent gets a one-line status; act on its final report.

## Steps

1. **Resolve the run.** For each of `baseBranch`, `bootstrap`, `verify`, `parallel`, `maxSlices`, `localOnly`: a flag wins, then `.claude/drive-spec.json` in the repo root, then the default. Defaults: repository default branch, no bootstrap, verify gate read from the repo's `CLAUDE.md` or `AGENTS.md`, parallel, no ceiling, no local-only slices. `--sequential` sets `parallel` to false. Resolve the worktree root per WORKTREES.md. A cloud session is one where `CLAUDE_CODE_REMOTE` is `true`. Its one VM runs every agent and gate, so there a parallel run builds at most `cloudMaxParallel` slices at once (default 2); `drive-spec` applies it, and `preview` prints it with the mode. Pin the resolved gate with `drive-spec gate <spec> '<verify>' --base <base>`, wherever it came from: every verdict in the run comes from `drive-spec verify`, which runs the pinned gate and only that gate; pinning marks the run's start, from which `maxSlices` counts landings, and writes `base` to the status file for every later command. Done when every value is printed with where it came from, and the gate is pinned.

   `localOnly` marks slices only the developer's machine can prove, such as tests that need a desktop app: `label` names them, and `proof` is a file in the repo saying how to prove one beyond the verify gate. In a cloud session these slices are **held**: never built, and anything they block waits. Locally they build one at a time, and their implementer also follows `proof`.

   `runProof` is a file in the repo saying how to run a change and watch it work: start the app or service, call it, look at the result. Every other slice's implementer follows it after the gate and reports what it saw, which goes in the slice PR's `Verification:`. Default: `.claude/skills/verify/SKILL.md` when the base branch has one; `false` turns it off.

2. **Guard the spec.** Run `drive-spec plan <spec>`, the script beside this file. It discovers the tracer-bullets and their blockers, orders them, and gives each slice's state: `closed`, `open-pr`, `in-flight`, `todo` or `held`. Exit 2 refuses the spec, with the reason on its `refuse:` line: run `drive-spec finish <spec> refused`, and stop. Done when the plan is printed: printed without `--json` in step 2, it also marks step 3 begun. Whenever a later step needs slice states again, run `drive-spec plan <spec> --json` rather than re-deriving them.

3. **Open the spec worktree.** Branch `agent/local-spec-<n>-<slug>` — the `local-` segment is load-bearing: a repo whose CI advances specs off merges into `agent/spec-*` would otherwise dispatch the next slice itself on every merge here and build it twice. `drive-spec open <spec> --base <base>` reuses the worktree, resumes the branch from origin, or cuts it from `origin/<base>` and pushes it, bootstraps a new worktree (its log is `<notes>/logs/bootstrap-spec-<n>.log`), and writes `branch` and `base` to the status file. Done when it prints the worktree: it is then on the spec branch at origin's HEAD.

4. **Preview.** `drive-spec preview <spec>`, with `--sequential` and `--max` as resolved in step 1, prints base, spec branch, worktree root, mode, ceiling and the plan, and posts or refreshes the progress comment. With `--dry-run`, add it to the command, which pauses the run there, and stop.

5. **Explore.** `drive-spec explore <spec>` writes the explorer brief; hand it to one general-purpose subagent. It writes notes for each open slice, naming the ADRs that bind it, `coverage.md` mapping every spec requirement to the slice that owns it, `questions.md` with each decision the spec leaves to the operator and each spec line an ADR contradicts, and `conflicts.md`. Done when `drive-spec explored <spec>` exits 0. It refuses, naming what to do, while a file is missing or older than the run, a requirement is `unmapped`, or a question has no answer: ask them all in one `drive-spec ask <spec> '<questions>' --ref Q1,Q2,…`, record each unmapped requirement's answer in `coverage.md`, then run it again. An answer that ships a slice in a PR of its own: `drive-spec defer <spec> <m> --why '<the answer>'`, and map its requirements `→ out of scope: …`. Exit 3: `conflicts.md` lists conflicts, and the command has halted the run before any build and posted the list; stop. The operator settles each conflict in the issues and resumes.

6. **Build the frontier.** Run `drive-spec build <spec>` in the background, as above, with `--sequential` and `--max` as resolved in step 1, until it exits 0. It runs the loop itself: it picks the frontier, starts each slice, launches each implementer, and a merger on a conflict, as an agent of its own from IMPLEMENTER.md and MERGER.md, integrates completed slices one at a time in finish order, lands each, and halts the run on red. It prints one line per slice event; the status file's `agents` map shows what runs and where each agent's log is (STATUS.md, Agents). Act on its exit code:
   - 0: `stop: done`, every slice closed: go to step 7.
   - 6: agents or gates still run, detached: run the same command again. It adopts them, so no slice builds twice.
   - 5: act on the inbox notes (STATUS.md, Inbox), then run it again.
   - 4: a slice halted, on its `halted #<m>: <reason>` line: `build` has run `drive-spec halt`, which finished the run. Stop.
   - 7: `stop: ceiling` or `stop: held`: `build` has finished the run as paused. Stop.
   - 1: a failed tracker or git call, which halts nothing: run the same command again. A second exit 1 in a row with the same message is not transient: stop and ask the operator (STATUS.md, Questions).
   - 2: a refusal, such as the `agent` command missing from the PATH, a slice carrying `agent:blocked` (once the operator says it is fixed, `drive-spec unblock <spec> <m>` clears it: the `agent:*` labels are drive-spec's to set and clear, never the orchestrator's), or another `build` of the spec still running: fix what it names, never route around it.

7. **Review the whole.** Run `drive-spec review <spec>` and do what it prints, until it prints `review clean`. Each call is one of: a round's reviewer brief (hand it to a reviewer subagent, which writes the round's findings file); a round's fixer brief, holding only that round's **rule** findings, each citing the written rule it breaks, and its **bug** findings, each saying how the change fails (hand it to an implementer subagent in the spec worktree); or clean. Between a fixer and the next round, `review` pushes the verified fixes itself. A **judgement** finding, or a **pre-existing** bug that base has too, never goes to a fixer: each round re-raises those still true, and the last round's become the left list. With a `REVIEW.md` on base, the repo's checklist, the reviewer applies each item whose trigger the diff matches and names them in the findings file. A fixer that reports a fix would change an operator answer has asked a question: `drive-spec ask` it. From round `reviewRounds` (default 3) on, a round's fixes go to a fixer while it raises only findings the round before did not; one that raises a rule or bug finding again (same rule, same file), or reaches twice the cap, makes `review` refuse before any fixer runs, until the operator answers whether to go on. Done when `drive-spec reviewed <spec>` exits 0: it refuses until the last round is a clean review of the pushed, green HEAD, and keeps the last round's judgement calls for `confirm`.

8. **Confirm the spec PR.** `drive-spec confirm <spec>`. With every slice closed and the spec branch HEAD green, it rewrites the draft's body to `Closes #<spec>`, the slices, a `Verification:` section (the gate, the spec HEAD's verdict, each slice's verdict and local or run proof), and the `Unverified:` and `Deviations:` lists their PRs reported, opens the draft first when absent, and keeps it draft, with step 7's `Left from review:` list when there is one.

9. **Clean up.** `drive-spec cleanup <spec>` removes the spec worktree, any slice worktree still present, and the notes directory, prunes, prints the PR URL, and marks step 10 begun in the status file. It refuses while a slice is open or the spec worktree holds uncommitted or unpushed work. The spec branch stays on origin until the PR merges.

10. **Review and fix the spec PR.** Run `/review-fix-pr <pr>` on the spec PR. It runs after step 9 because it opens the PR head in a worktree of its own and refuses a head checked out elsewhere. The PR stays draft. A run whose PR already carries a `review-fix-pr done` comment newer than the spec branch's last push skips this step. Its fix pass going red halts the run: `drive-spec finish <spec> halted --why '<why>' --step review-pr --resume '/review-fix-pr <pr>'`. Done when its status comment is on the PR; then `drive-spec qa <spec>`, which marks step 11 begun.

11. **QA the spec PR.** Hand the prompt `drive-spec qa <spec>` prints to a QA subagent, which runs `/qa-pr <pr>` on the spec PR: it runs the app at the PR head, walks every scenario in a browser, and posts the evidence on the PR. A run whose PR already carries a `qa-pr done` comment naming the spec branch's HEAD skips this step. A failed scenario halts the run: `drive-spec finish <spec> halted --why '<why>' --step qa-pr --resume 'drive-spec qa <spec>'`. Done when its comment is on the PR with no failed scenario; then `drive-spec finish <spec> done`. Scenarios it could not verify stay listed in its comment for the operator. With `"qa": false` in `.claude/drive-spec.json`, for a repo with no app to run, `drive-spec qa` says so and points straight at `drive-spec finish <spec> done`: skip `/qa-pr`.

Every run ends with `drive-spec finish` or `drive-spec halt`, never both: they post the status comment the operator is notified by, and write the final status. The run's last message opens with what that command printed, word for word, its `Left from review:` list included, then any summary of your own. Only `--dry-run` ends without either, on `drive-spec preview --dry-run`'s `paused` status. `finish` also records, once each, what the spec PR's own review and QA caught after step 7 passed it: `drive-spec misses` lists them across specs, and one that recurs is a `REVIEW.md` item worth writing. `finish` refuses an outcome the tracker contradicts, such as `done` with a slice still open, or, unless `qa` is `false`, with no `qa-pr done` comment naming the PR head with 0 failed.
